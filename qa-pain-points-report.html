QAPulse — Internal Review

Twenty-four pain points, traced to fixes

The same findings, now walked in test-cycle order — from the moment a requirement lands to the moment a release ships — with four gaps still honestly open.

Ref QAP‑REV‑2026‑07 Rev 3 Date 23 Jul 2026 Scope CR001–CR053

QA testing generates a specific, recurring set of frustrations — proving coverage, chasing a bug through a tracker, telling a stale pass from a real one. This review pairs each one against the QAPulse change request that shipped the fix, grounded in the 53 change requests already deployed to the system, not the proposals sitting alongside them.

Rev 3 keeps every finding and every citation from Rev 2 — re-verified against the running code, not just the change-log — and reorders them into the actual sequence a test cycle runs in, first stage to last, so it reads as a flow rather than a category list.

01 Intake→02 Authoring→03 Planning→04 Execution→05 Defect Logging→06 Resolution→07 Escape Analysis→08 Reporting

01Requirement Intake & Understanding

1 finding

An unclear requirement meant chasing someone over chat to ask what it meant.

Clarifying a vague requirement lived outside the tool entirely, in whatever thread the question happened to land in.

CR039

Requirement Q&A Chat — ask in plain language; the assistant resolves which requirement you mean (or asks which of a few candidates) and answers grounded in its actual content.

02Test Case Authoring & Library

3 findings + 1 open

Test cases lived in scattered spreadsheets, not one library.

Every project kept its own copy on a shared drive — reusing a test case for a new project meant hunting down whoever had it last.

CORE

A single Test Case Library, searchable by project, module, tag, and linked requirement, with clone / bulk-clone for reuse across projects.

Writing test cases started from a blank page every time.

Turning a new requirement into a full set of test steps was manual, requirement by requirement.

CR006 · CR015 · CR022 Pt.1

AI-assisted generation drafts test cases per requirement, grounded in its acceptance criteria, saving each batch back to the correct requirement rather than one bundled group.

Editing a shared test case meant editing blind.

Changing or deleting a library test case gave no warning about which live execution runs depended on it.

CR018

Execution drill-down — the "In N runs" badge opens every execution file using that test case before you touch it.

A test case has no version to roll back to.

Deleting a critical step by accident has no undo — only a record that it happened.

OPEN · Test case versioning

Half-solved: the audit trail (CR011) shows who changed what and when, but there is no version snapshot and no one-click rollback.

03Planning: Resourcing, Risk & Access

3 findings + 1 open

Nobody could see who was overloaded until a milestone was already slipping.

Resource load was invisible across projects — a tester could be double-booked across two active milestones with no signal to anyone.

CR034 · CR036 · CR038

A department-wide Resources page with an overallocation flag for anyone spanning two or more active milestones, plus utilization %.

Risks lived in someone's head, not in the system.

"This could slip because of X" got said in a meeting and never written down anywhere QA or PM could revisit later.

CR033 · CR037 · CR040

A dedicated Risk Register, plus an AI Risk Predictor synthesizing schedule drift, defect trends, and coverage gaps into an on-demand milestone risk read.

Nobody could say for certain who was allowed to do what.

Role permissions existed in code, not anywhere a lead could actually look them up.

CR041 · CR043

An Access Matrix page with a RACI overlay, viewable without reading the source.

There's no shared home for reusable test data.

Mock datasets get regenerated or copy-pasted per test cycle instead of stored once and reused ahead of a run.

OPEN · Test data management

Proposed, not built.

04Test Execution

3 findings + 1 open

Two testers on the same execution file didn't know about each other's saves.

A colleague's update to a shared execution file was invisible until you happened to refresh the page.

CORE

Every save on an execution file broadcasts a live update to anyone else viewing it — confirmed in test-execution.ts — no polling, no stale screen.

A pass from last sprint still read as a pass.

A test case last executed weeks ago kept showing green, indistinguishable from one actually verified this sprint.

CR017

Sprint-scoped result resolution — with a milestone selected, anything not re-run this sprint shows Not Run instead of stale green.

The spec moved mid-cycle and nobody testing against it was told.

A requirement's description changed after approval — by hand, or by re-pulling an updated Redmine ticket — and test cases already written and executed against the old wording stayed silently unflagged.

CR023 Pt.4

Revision alerts — any description change, including a Redmine resync, flags every linked test case and task "Alert: Revised" until acknowledged. Verified directly in requirements.ts: both paths run through the same update handler.

Automation results still don't reach QAPulse on their own.

A Playwright or Cypress run has no path into an execution file without someone manually transcribing the result.

OPEN · CR009 · CR010

Both a reporter and an in-app "Run Automation" trigger are designed and registered as change requests; neither has shipped.

05Defect Logging & Tracking

5 findings + 1 open

Defect numbers were retyped, and sometimes wrong.

A tester copied a Redmine ID by hand into the execution sheet — one transposed digit and the link to the real ticket was broken.

CR019

Auto defect creation — failing a step creates the Redmine ticket and writes the real ID back automatically.

Duplicate bug reports piled up because nobody checked what already existed.

Two testers hitting the same failure often filed two separate tickets, doubling the tracker's noise.

CR019

The fail modal runs a duplicate check against the tracker before a new defect is created.

A tracker outage stopped testing outright.

If Redmine was unreachable, there was no way to log a failure at all — testers waited instead of working.

CR019

"Never block on Redmine" — a failed step saves locally as pending sync and pushes through once the tracker is back.

No pattern showed which kind of defect kept recurring.

Bugs were logged as free text — nothing separated a performance regression from a UI slip from a security gap.

CR029

A fixed ten-category defect taxonomy applies at both creation points, feeding density-by-module reporting.

A wrong requirement had nowhere to go once approved.

The only outlet for "this requirement is ambiguous or contradictory" was rejecting it during the original review — a door that shut the moment it was approved.

CR031

Requirement defect workflow — authoring problems now get the same severity, assignee, and tracking as a code defect.

Redmine is the only tracker QAPulse talks to.

A Jira-based team gets none of the auto-defect-creation or sync behavior above — every integration in this report is Redmine-specific.

OPEN · Jira / multi-tracker

Proposed, not built. No Jira code exists anywhere in the repository today.

06Defect Resolution & Rework Loops

4 findings

"Fixed" didn't mean retested.

A developer closed a bug; nobody was prompted to confirm the linked test case actually passed afterward.

CR019 · CR020

Retest-needed flag — a defect marked fixed while its test case is still Failed surfaces under Awaiting Retest automatically.

"Ready for QA" had no way back.

If a developer marked work ready too early, QA's only recourse was chasing them over chat while every dashboard kept showing "Ready."

CR046 · CR052

Return to Dev — QA bounces work back with a reason, and the timeline correctly counts the rework as development time, not testing time.

A bad requirement, not just a bad build, had no return path.

When dev or QA found the approved requirement itself was wrong, filing a code defect against it didn't fix the source.

CR053

Return to FA — a dedicated action reopens the requirement for its author to revise, tracked as its own rework cycle.

Review actions arrived late, or not at all.

A rejection or a retest request sat in a generic notification feed, unrouted, on a thirty-second poll.

CR027

Real-time notification center — nine structured event types push instantly and deep-link straight to the item.

07Production Escape Analysis

1 finding

Bugs that escaped to production were patched, not investigated.

An incident got fixed with no record of whether a coverage gap, a skipped test, or a bad pass let it through.

CR020

Escape analysis — every production defect is classified (coverage gap / selection gap / wrongly passed), with one-click regression test creation and a tracked leakage rate.

08Reporting, Sign-off & Compliance

4 findings

Quality trend required manual detective work.

A QA lead proving "are we improving sprint over sprint" had to stitch together the execution file, the defect tracker, and the traceability matrix by hand — no view answered it directly.

CR026

QA Analytics Dashboard — execution trend, velocity, pass rate by milestone, defect density and escape funnel, coverage snapshot, all on one page.

Proving coverage meant building the matrix by hand.

Mapping every requirement to its test cases and defects for a stakeholder sign-off had no supporting tool — it was a spreadsheet exercise every time.

CR005 · CR016

Traceability Matrix with full requirement-hierarchy rollup, deduped by test case identity, exportable to Excel.

QA absorbed the blame for delays it didn't cause.

When a milestone slipped, the read was "testing ran long" — with no record of how long requirements sign-off or dev handoff had already taken.

CR014 · CR032 · CR052

Phase-breakdown timeline — Requirements, Dev, QA, and UAT are timestamped separately, so a slip shows exactly where it sat.

A changed test result left no fingerprints.

Nothing recorded who flipped a Pass to a Fail, or when — an unanswerable question the moment a compliance review asked it.

CR011

Audit trail — every result change, assignment, and status transition is logged, searchable by entity and date range.
